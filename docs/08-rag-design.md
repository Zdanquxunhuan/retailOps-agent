# 08 RAG 知识库

## 必要性与位置

RAG 服务于解释错误码、引用业务规则、推荐经过审核的 SOP。诊断初期可检索应采集哪些证据，收集后再按异常类别检索支持结论的知识；调用预算由 Workflow 管理。实时订单查询必须使用业务工具，不能从历史案例回答当前状态。

## 入库流程

来源登记 → 访问权限与敏感信息检查 → 文档解析 → 结构切分 → 人工审核 → Embedding → 索引构建 → 原子发布知识版本。未审核资料不能成为生产补推依据。订单数据和原始客户日志不整体入库。

每个 chunk 保存 documentId、version、sourceUri、section/page、contentHash、platform、businessType、environment、systemVersion、effectiveFrom/To、accessScope、approvalStatus、embeddingModelRevision。错误码与表格按语义单元保留，不能把码值和处理说明切开。初始 400–800 token、约 10% 重叠作为实验参数，由真实中文 SOP 评估调整。

## 检索与引用

先由服务端确定租户、环境、平台、业务和可见性过滤，再检索。BGE-M3 的官方模型卡说明支持 dense/sparse/multi-vector，本项目第一版只使用 dense，不宣称已经实现其全部检索方式。[模型卡](https://huggingface.co/BAAI/bge-m3)

选 PostgreSQL/pgvector 减少运维组件。初版保存 dense 向量，并对错误码、接口名建立精确关键词索引；中文关键词采用经过验证的分词策略，不假设 PostgreSQL 默认全文检索等于中文 BM25。知识规模小时可先精确向量查询，达到容量瓶颈再建立 ANN 索引并评估过滤后的召回。

对比 dense-only、关键词+dense 融合（RRF）、融合+重排三组。暂定召回 20 条、上下文 5 条；重排仅在质量提升足以抵偿延迟时启用。BGE 模型的版本、向量维度、归一化与相似度方式必须在服务探测与入库时锁定；不允许把不同 Embedding 版本向量混查。

引用格式为 documentId@version#section，报告同时引用 evidenceId。CitationValidator 校验引用存在、用户可见、版本有效，并验证结论是否真正由片段支持。无来源时输出“建议进一步核实”，不能生成虚构链接。

## 生命周期和历史案例

知识更新生成新版本索引，完成回归后切换 activeVersion，旧任务保留当时引用版本；撤销权限立即禁止再次检索和展示，即使任务缓存曾经包含该片段。文档删除同时处理向量、缓存与引用访问策略。

历史案例由工单根因、证据摘要、处理动作、最终核验、业务审核组成。模型生成的诊断必须人工确认后才能发布为知识，避免错误自我强化。相似案例只支持假设，不能成为执行授权。

## 评估与失效降级

按平台/场景/文档版本切分训练调优与测试集，防止同一工单变体泄漏。测 Recall@5、MRR、引用正确率、越权召回数、无答案拒答率。做移除 RAG 的消融对比，证明知识检索是否有价值。知识服务失败仍返回实时证据报告；引用失效不允许支撑高风险动作。
