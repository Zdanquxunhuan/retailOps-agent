# 00 项目定位与可行性

## 结论

需求适合 Agent，但核心价值不是让模型直接补推，而是把分散证据转化为可验证的诊断，并在确定性策略允许时提出处理计划。系统定位为内部订单运维入口，用户是研发运维、业务支持、门店授权查询人员及审批人。

自然语言具有平台简称、业务歧义、缺失参数；故障证据分散在日志、数据库、平台及 POS，各系统表达不同。这些是 LLM 信息提取、假设生成、证据关联和解释能力发挥价值的地方。接口状态判定、权限、审批、幂等与执行恢复则必须由 Java 保障。

| 能力 | 采用方式 | 验证价值 |
|---|---|---|
| 用户意图、缺参澄清 | LLM 输出受 Schema 约束的候选信息 | 与人工标注意图、槽位对比 |
| 动态取证 | Agent 在当前节点允许的只读工具内选择补充证据 | 比较固定全量查询的工具次数与正确率 |
| 故障解释 | LLM 综合实时证据与 SOP，并标注支持与冲突 | 根因分类、引用真实性、拒答率 |
| 业务状态、重试和补推 | 持久化 Java 状态机 | 并发、超时、宕机、审批失效测试 |
| 已知错误码诊断 | Java 规则优先 | 无模型也能返回确定事实 |

## Agent 技术取舍

单 Agent 搭配五类诊断策略更合适。平台隔离是适配器和权限上下文隔离，并不要求每个平台增加一个 LLM。日志、本地订单、POS 只读查询可由 Java 并行调度；并行 I/O 不等于多 Agent。只有多专长上下文冲突、独立评估和路由收益被测量证明时，才评估增加 Specialist。

RAG 在第二个增量引入：用于引用接口说明、错误码、SOP 与经审核历史案例。它不能代替实时订单查询，不能把旧案例当作当前订单的事实。MVP 可先用少量版本化 SOP 和规则，检索能力独立验收。

MCP 是跨客户端复用工具的可选协议；现有 Java 8 系统通过 HTTP 适配即可接入，不需要先升级或改造成 MCP Server。MVP 不引入 MCP 服务；出现第二类工具消费方后再做只读 MCP 试点。

## MVP 与业务收益

首个可演示 MVP 仅覆盖美团销售：单订单自然语言输入、必要参数追问、跨实例日志覆盖报告、本地/平台/POS 查询、证据报告、历史诊断查看；全部使用 Mock 或明确授权测试环境。缺少 POS 查询能力时必须报告“无法验证”，不会虚构成功。

业务收益通过同一批故障的人工排查基线衡量：从请求到有效结论的耗时、人工接触次数、正确根因率、证据充分率；补推阶段另外统计重复业务写入和最终核验成功率。首轮没有真实数据，所有性能及效果指标均为验收目标，不是实测收益。

## 约束与风险

- 日志不完整是主要业务风险：必须返回实例覆盖范围、轮转缺失和时间范围，不能把缺证当作无订单。
- 旧系统无幂等或 POS 无查询时，无法保证自动修复安全；降级为诊断和人工处理，不通过模型补足缺失能力。
- 外部模型只接收最小脱敏证据，生产数据外发需企业策略允许。未允许则使用本地/测试数据或禁用模型出口。
- LLM 失败时仍能返回已收集的事实和工具异常，故障排查不依赖模型可用性。
- 初期部署目标是小范围内网使用；容量、保留期、RTO/RPO 需基于实际门店和订单规模复核。
